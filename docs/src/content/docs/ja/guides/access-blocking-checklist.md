title: 付録：アクセス遮断チェックリスト
description: セッション失効・アカウント停止・管理操作・監査・運用検証の確認項目。
---

アクセス遮断に関する機能と運用を確認するためのチェックリストです。このエディションの実装・既存テスト・ドキュメントで確認できる項目にチェックを付けています。網羅的な監査や、本番環境での検証結果を示すものではありません。

:::note[このエディションの責務と拡張方針]
このエディションは、ユーザー本人によるアカウント保護と、運用者向けのセッション失効CLIを中心にしています。管理者向けのユーザー管理機能は備えていません。

アカウントの停止・解除まで扱うには、管理者権限、各認証経路での停止状態の検査、操作の監査などが必要になり、変更範囲と責務が大きく広がります。導入する場合は、別ブランチで管理機能を拡張する方針です。この一覧の未チェック項目は、このエディションの不足を一律に示すものではなく、拡張時に検討する範囲も含みます。
:::

:::note[チェックの対象範囲]
セッション失効は `SESSION_DRIVER=database` が前提です。チェックはこの構成での既存セッションの失効を対象とし、アカウントの一時停止や新規ログインの禁止を意味しません。未チェックには、未実装・対象外・運用側で未確認の項目が含まれます。
:::

## 1. セッションの遮断

- [x] 特定ユーザーのすべての認証済みセッションを強制失効できるか
  - [x] PC・スマートフォンなど複数端末のセッションを失効できるか
  - [x] ユーザー本人の操作なしに管理者が失効させられるか
  - [x] 失効したセッションを利用した次回アクセスが拒否されるか
  - [x] Remember Meなどによる自動再認証も無効化できるか

:::tip[実装とテスト]
`security:revoke-sessions` が対象ユーザーの保存済みセッションを削除し、Remember meトークンを更新します。複数クライアント・コピーしたCookie・Remember me Cookieの失効を既存テストで検査しています。CLIの実行権限はサーバー側で管理する必要があります。
:::

## 2. アカウントの一時停止

- [ ] 特定ユーザーのアカウントを一時停止できるか
  - [ ] 停止中は新規ログインを拒否できるか
  - [ ] 停止前に認証されたセッションからのアクセスも遮断できるか
  - [ ] パスワード・パスキーなど、すべての認証方式に適用されるか
  - [ ] パスワードリセットなどで停止状態を回避できないか
  - [ ] 管理者が停止を解除できるか

:::note[追加実装の範囲]
アカウントの停止状態や停止・解除操作は未実装です。セッションを失効しても、有効な認証情報による新規ログインは可能です。
:::

## 3. 遮断操作の実行

- [x] 管理者が遮断操作を実行する手段が存在するか
  - [x] 管理画面またはCLIなどから操作できるか
  - [x] 遮断対象をユーザーIDなどで正確に指定できるか
  - [x] 遮断操作の成否を確認できるか
  - [ ] 権限のないユーザーによる遮断・解除操作を禁止できるか

:::note[CLIの実行権限]
ここでチェックした操作はCLIによるセッション失効です。`id:123`・`email:user@example.com` で指定し、実行結果・エラー表示と終了コードを確認できます。アプリケーション内の管理者ロールによるCLIの権限判定はなく、サーバーへのアクセス権限の制限は運用側で確認します。
:::

## 4. 遮断操作の監査

- [ ] 遮断および解除の操作履歴が記録されるか
  - [ ] 操作日時が記録されるか
  - [ ] 操作者と対象ユーザーを区別して記録できるか
  - [ ] 遮断・解除の種類と結果が記録されるか
  - [ ] 必要に応じて操作理由を記録できるか

:::note[監査の追加が必要です]
セッション失効の専用監査イベントや、操作者・操作理由の記録はありません。アカウント変更のセキュリティイベントが存在することだけでは、この分類を充足しません。
:::

## 5. 認証トークンの無効化【APIトークン認証を利用する場合】

- [ ] APIトークンなどセッション以外の認証手段を無効化できるか
  - [ ] 特定ユーザーの発行済みトークンを一括失効できるか
  - [ ] 特定のトークンのみ失効できるか
  - [ ] アカウント停止中にトークンによるアクセスを防止できるか

:::note[このキットでは対象外]
このキットにはAPIトークン認証を組み込んでいないため、現状は対象外です。追加する場合は、トークンの失効と停止状態の検査を別途確認してください。
:::

## 6. 個別セッションの管理【追加実装可能】

- [x] ユーザーの有効なセッションを一覧で確認できるか
- [x] 特定の端末・セッションのみ失効できるか
- [x] ユーザー本人が他端末のセッションを失効できるか

:::tip[本人向けのセッション管理]
本人の設定画面で一覧・個別失効・ほかのセッションの一括失効を利用できます。個別失効でもRemember meトークンはユーザー全体で更新します。管理者が別ユーザーの個別セッションを操作する画面はありません。
:::

## 7. 緊急時の遮断【追加実装可能】

- [ ] 全ユーザーのセッションを一括失効できるか
- [x] アプリケーションへのアクセスを一時的に制限できるか
- [ ] 重大な異常検知を契機として自動遮断する仕組みを追加できるか

:::note[メンテナンスモードでの対応]
一時的なアクセス制限にはLaravel標準のメンテナンスモード（`php artisan down`、解除は `php artisan up`）を使えます。これは全ユーザーのセッション失効ではなく、処理中のリクエストを中断する機能でもありません。全ユーザーのセッションを失効する専用コマンドや異常検知による自動遮断は未実装です。

全体遮断や自動遮断は業務停止・誤検知の影響が大きいため、必要性に応じて導入を検討します。
:::

## 8. 運用・検証【運用側で確認】

- [x] 遮断操作の実行手順が文書化されているか
- [ ] 管理者が緊急時に遮断操作を実行できるか
- [x] 複数端末でログインした状態から、全セッションの遮断を検証できるか
- [ ] アカウント停止後に再ログインできないことを検証できるか
- [ ] 遮断を解除し、正常な認証で利用を再開できるか

:::note[運用環境での確認]
[セッション管理](../../sessions/)にブラウザーとCLIの操作手順を記載しています。複数クライアントの失効テストもありますが、本番環境の権限・緊急時の実行体制は運用側での確認が必要です。
:::

## 9. 遮断の確実性

- [ ] アカウント停止状態を認証済みリクエストでも検査できるか
- [ ] Web・APIなど、すべての対象アクセス経路に遮断が適用されるか
- [x] Remember Meによる自動再認証を防止できるか
- [x] 利用中のセッション保存方式で強制失効が保証されるか
- [ ] セッション削除とログインが競合しても停止状態を回避できないか
- [ ] 遮断の反映タイミングが定義されているか
- [x] セッション失効とアカウント停止の違いが明確か
- [ ] アカウント停止を解除しても、失効済みセッションが復活しないか

:::caution[database構成での確認です]
保存方式のチェックはdatabase構成に限ります。file・Redisなどではこのキットの失効機能は利用できません。ログインとの競合、処理中のリクエスト、すべてのアクセス経路を含む遮断タイミングの保証は、このチェックに含めていません。
:::

## 10. 管理機能の安全性と自動テスト

- [ ] 遮断・解除を実行できる管理者権限が明確か
- [ ] 権限チェックをサーバー側で強制しているか
- [ ] 管理操作にCSRF対策や必要な再認証が適用されるか
- [ ] 管理者自身や最終管理者を遮断する場合の扱いが定義されているか
- [ ] 不正な遮断操作や失敗も監査対象になるか
- [x] 複数端末からのアクセス遮断を自動テストできるか
- [ ] パスワード・パスキー等の認証方式ごとに停止を検証できるか
- [ ] 停止・解除・再ログインまでの一連のテストが存在するか

:::tip[自動テストの対象]
`SessionManagementTest` と `RevokeUserSessionsCommandTest` が複数クライアントの失効を検査します。本人向けWeb操作には認証・本人確認・他ユーザーのセッションを拒否する検査がありますが、管理者による停止・解除機能の権限検査とは別のため、その項目は未チェックです。詳細は[テスト項目一覧](../tests/)を参照してください。
:::

## 判定基準

- **実装済み**：機能が存在し、期待する遮断動作を確認できる
- **部分実装**：機能は存在するが、特定の認証方式やアクセス経路を遮断できない
- **未実装**：遮断手段が存在しない
- **対象外**：対象となる認証方式・機能を利用していない

## 実装上の基本方針

1. 既存の認証基盤を活用し、独自の認証処理を不必要に増やさない。
2. セッション失効とアカウント停止は別の操作として扱う。
3. 遮断操作は手動実行できることを優先する。
4. 遮断・解除は監査対象とする。
5. 自動遮断、個別セッション管理、全体遮断は必要に応じて追加する。
6. WAF・ネットワーク遮断・インフラ側のアクセス制限は別チェックリストで扱う。
