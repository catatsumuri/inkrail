本番環境では、Webアプリケーションに加え、利用する機能に応じてキューワーカーとスケジューラーを稼働させます。この章では、このキットの追加機能を運用するための設定と確認項目をまとめます。

以下のコマンドは、アプリケーションのルートで実行してください。実際の接続先やプロセスの管理方法は、デプロイ先の環境に合わせて設定します。

アクセス遮断の機能と運用を確認するための[付録：アクセス遮断チェックリスト](../guides/access-blocking-checklist/)も用意しています。このエディションで確認できる項目にチェックを付け、適用条件と未実装の範囲を補足しています。

## 本番環境の設定

### アプリケーションと接続先

`.env.example` は開発を始めるための設定です。本番では少なくとも次の項目を確認してください。

| 項目 | 確認する内容 |
| --- | --- |
| `APP_ENV` | 本番では `production` に設定します。 |
| `APP_DEBUG` | `false` にして、エラーの詳細を画面へ表示しないようにします。 |
| `APP_URL` | 公開先のHTTPS URLを指定します。メール内のリンクやパスキーの設定にも使います。 |
| `APP_KEY` | 初回に生成したキーを安全に保管し、デプロイのたびに作り直さないでください。 |
| `DB_*` | 本番用データベースの接続先と認証情報を指定します。 |
| `SESSION_DRIVER` | このキットのセッション一覧・失効機能を使う場合は `database` が必要です。 |
| `CACHE_STORE` | レート制限とアラートの重複抑制に使います。複数インスタンスでは共有できるストアを用意します。 |
| `MAIL_*` | 実際にメールを配信できるサービスを指定します。`MAIL_MAILER=log` では受信者に届きません。 |
| `ALERT_MAIL_TO` | 例外・ジョブ失敗アラートを受け取る運用者のメールアドレスを指定します。 |
| `AUDIT_SECURITY_VIEWERS` | セキュリティイベントを閲覧できるユーザーのメールアドレスをカンマ区切りで指定します。 |
| `AUDIT_SECURITY_RETENTION_DAYS` | セキュリティイベントの保持日数を正の整数で指定します。既定値は365日です。 |

パスキーを使う場合は、公開先のホスト名と `APP_URL` が一致することを確認してください。セキュリティイベントの閲覧には、許可リストへの登録に加えてメールアドレスの確認が必要です。

本番環境では、パスワードの既定ルールも強化されます。12文字以上、英大文字・小文字、数字、記号を要求し、漏えい済みパスワードの検査を行います。

### デプロイ時の反映

依存関係とフロントエンドのビルド成果物を用意し、データベースの変更と設定を反映します。次は主なコマンドの例です。マイグレーションの内容を確認し、必要なバックアップを取得したうえで実行してください。

```sh
php artisan migrate --force
php artisan config:cache
php artisan view:cache
```

フロントエンドは `npm run build` で作成した `public/build/` を配置します。Webサーバーの公開ディレクトリは `public/` とし、実行ユーザーが `storage/` と `bootstrap/cache/` に書き込めるようにします。

設定をキャッシュすると、`.env` を編集するだけでは実行中の設定に反映されません。変更後に `config:cache` を再実行し、キューワーカーなどの常駐プロセスも再起動してください。

:::note[セッション管理にはデータベースが必要です]
Redisやfileなどのセッションドライバーでもアプリケーションは利用できますが、このキットの一覧・失効機能は使えません。設定とテーブルの準備は[セッション管理](../sessions/)を参照してください。
:::

## キューとスケジューラー

### キューワーカー

`QUEUE_CONNECTION=database` など、非同期のキューへジョブを投入する場合はワーカーを起動します。databaseキューでは、マイグレーションで `jobs`・`failed_jobs` などのテーブルも用意します。

```sh
php artisan queue:work
```

本番ではプロセスマネージャーなどで常時稼働させ、終了時に再起動するようにします。ワーカーは起動時のコードと設定を保持するため、デプロイ後は次のコマンドで再起動を促します。

```sh
php artisan queue:restart
```

`queue:restart` は、ワーカーを新しく起動するコマンドではありません。処理中のジョブを終えて終了した後に、プロセスマネージャーが起動し直す構成にしてください。

このキットの `GeneralNotification` 自体はキューを使わず送信します。アカウント変更通知のレスポンス後の配信も、キューワーカーによる再試行ではありません。通知の配信方法と制約は[通知と運用アラート](../notifications/)を参照してください。

### スケジューラー

セキュリティイベントの保持期間に応じた削除は、`routes/console.php` で1日1回実行するよう登録されています。登録だけでは動かないため、本番では毎分 `schedule:run` を起動するcronなどを設定してください。

```text
* * * * * cd /path/to/application && php artisan schedule:run >> /dev/null 2>&1
```

`/path/to/application` とPHPの実行パスは環境に合わせます。複数インスタンスで稼働させる場合、このキットの削除タスクには単一サーバーでの実行を保証する指定がないため、スケジューラーを実行するインスタンスを決めてください。

登録内容と次回実行時刻は次のコマンドで確認できます。実行時刻はアプリケーションのタイムゾーンに従い、このプロジェクトの既定値はUTCです。

```sh
php artisan schedule:list
```

開発中に継続実行する場合は `php artisan schedule:work` を使えます。

保持日数が正の整数でない場合、削除タスクは登録されず、設定エラーが報告されます。削除の詳細と手動実行は[セキュリティイベント](../events/)を参照してください。

## 運用時の確認項目

### 起動・デプロイ後

| 確認対象 | 確認する内容 |
| --- | --- |
| アプリケーション | `/up` が応答することに加え、ログインと主要画面を確認します。 |
| メール | アカウント変更通知と運用アラートが、想定した宛先へ届くことを確認します。 |
| セッション | 一覧が表示され、不要なセッションを失効できることを確認します。 |
| イベント閲覧 | 許可されたユーザーだけが `/admin/security-events` を閲覧できることを確認します。 |
| キュー | ワーカーが稼働し、ジョブが滞留していないことを確認します。 |
| 保持期間 | スケジューラーが稼働し、削除タスクが登録されていることを確認します。 |
| 保存領域 | データベース、ログ、バックアップの容量と保存期間を確認します。 |

`/up` の応答だけでは、メール配信やキューワーカー、スケジューラーまで正常に稼働しているとは判断できません。それぞれの実行結果も確認してください。

### アラートやジョブ失敗を調べる

運用アラートは、同じ例外クラス・ファイル・行番号の通知を5分間抑制します。メールの件数と実際のエラー件数は一致しないため、アプリケーションのログも確認してください。初期設定のログ出力先は `storage/logs/laravel.log` です。

失敗したジョブは次のコマンドで一覧を確認できます。

```sh
php artisan queue:failed
```

原因を修正した後、再実行してよいジョブだけを選びます。メール送信や外部サービスへの登録など、途中まで処理が進んでいる可能性があるため、重複実行の影響を確認してください。

```sh
php artisan queue:retry <ジョブID>
```

アラートそのものの配信に失敗した場合は、`Failed to send alert notification.` が警告ログに記録されます。宛先、メールサービスの接続設定、サービス側のエラーを確認してください。

### 不審な操作への対応と記録の保全

不審なアカウント変更やログインが疑われる場合は、[セキュリティイベント](../events/)で記録を確認し、必要に応じて[CLIから対象ユーザーのセッションを失効](../sessions/#cliでセッションを失効させる)させます。失効には `database` セッションドライバーが必要で、既存の「`Remember me`」によるログインも無効化します。

イベントの記録と通知は、失敗しても元のアカウント操作を妨げない設計です。記録やメールがないことだけを根拠に、操作がなかったとは判断しないでください。

セキュリティイベントのモデルには更新・削除を拒否する保護がありますが、直接のSQLや一括操作まで防ぐものではありません。保持期間による削除も一括操作で行います。調査に必要な記録は削除前に保全し、データベースのアクセス権限とバックアップを別途管理してください。
