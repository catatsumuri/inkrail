# Feature flags

The `extended` line of this starter kit lets you switch some authentication
features off with environment variables. This document explains what the
flags are, how to use them safely, and how to add one.

## What they are

These are **deployment-time** flags. They are read once, while the
application boots, and Fortify decides which routes exist at that moment.
They are not per-request switches, and changing `.env` does not affect
running processes.

After changing a flag:

1. Clear or rebuild the config cache (`php artisan config:clear`, or
   `config:cache` in production).
2. Restart long-lived processes (Octane, queue workers, and so on).
3. Rebuild the frontend (`npm run build`) if the flag is shown or hidden in
   the UI.

Set the same values in every environment, including CI.

## Why flags instead of Chisel

Laravel's Chisel asks which features to keep at install time and then
**deletes the code** of the others. That is the safest way to switch a feature
off, because it cannot be switched back on by accident. Its weakness is that
the result no longer matches upstream: the files are rewritten and removed,
so later upstream changes to them can only be merged by hand.

The flags keep every file in place and leave the Chisel markers
(`@chisel-...`) untouched, so upstream changes still merge. The price is
that the code, controllers, models and database tables of a disabled feature
stay in the application; only the routes and UI are turned off.

Because nothing is deleted, a flag can also be turned back on. That is
convenient in development and a risk in production. Treat the flags as
**decisions you make once, before launch**.

## The flags

All flags default to `true`. They are defined in `config/features.php`.

| Variable                        | When `false`                                                                                                                 |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `FEATURE_REGISTRATION`          | Registration routes are not registered; the "Sign up" and "Register" links are hidden.                                       |
| `FEATURE_PASSKEYS`              | Passkey routes and `/.well-known/passkey-endpoints` are not registered; passkey buttons and management are hidden.           |
| `FEATURE_TWO_FACTOR`            | Two-factor setup, recovery-code and challenge routes are not registered; the security page hides the section.                |
| `FEATURE_PASSWORD_CONFIRMATION` | Sensitive operations no longer ask for a recent password confirmation, and the browser session-management pages are removed. |

## Read before turning one off

- **Two-factor authentication.** With the flag off, Fortify no longer adds the
  challenge to the login flow, so accounts that already enrolled can sign in
  with their password alone. Do not turn this off once users have enrolled.
- **Passkeys.** Existing passkeys stop working while the flag is off. Their
  data is kept and works again if the flag is re-enabled.
- **Password confirmation.** Fortify's own `password.confirm` routes remain;
  they are simply no longer required anywhere. Removing session management
  with it is a policy choice carried over from Chisel, not a technical
  dependency.
- **Registration.** Turning it off stops self-service sign-up; it does not
  affect existing accounts.
- **Data and migrations are never touched.** Columns and tables for disabled
  features stay in the database.

## Frontend and Wayfinder

The pages import route helpers generated by Wayfinder for every feature. While
`wayfinder:generate` runs, `FeatureFlagServiceProvider` forces the
route-affecting flags on, so generated files always describe the full route
set. HTTP requests still honour the flags. Without this, a disabled flag would
remove a helper the pages import and break the build.

## Adding a flag

1. Add the variable to `config/features.php` and `.env.example`.
2. If it removes a Fortify feature, add it to the map in
   `App\Providers\FeatureFlagServiceProvider`.
3. If it adds or removes routes, add it to the list forced on during
   `wayfinder:generate` in the same provider.
4. If the UI depends on it, share it from `HandleInertiaRequests` and add it
   to the shared props type in `resources/js/types/global.d.ts`.
5. Write a test that boots the application with the flag off, using
   `Tests\Concerns\BootsWithFeaturesDisabled`. Changing `config()` inside a
   running test cannot remove routes that are already registered.
6. Document the consequences of turning it off in this file.
